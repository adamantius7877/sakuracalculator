# Shared Food API

This document describes how another local app, such as `MealsAndGroceryDashboard`, can share the CaloriesDashboard food database.

## Tech Stack

- Frontend and API: Next.js app router, React, TypeScript.
- Runtime: Node.js inside the app container.
- Database: PostgreSQL 16, provided by `postgres:16-alpine` in Docker Compose.
- Deployment: `compose.yml`, `Dockerfile`, and PowerShell scripts in `scripts/`.
- Migrations: `node scripts/migrate.mjs` runs SQL files from `db/migrations/` on container startup.

## Docker Services

The default deployment runs two services:

- `db`: PostgreSQL database with a persistent `postgres-data` Docker volume.
- `app`: CaloriesDashboard web app and API.

The app receives:

- `DATABASE_URL=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}`
- `DATABASE_SSL=false`
- `FDC_API_KEY=` for USDA FoodData Central lookup.
- `ALLOWED_ORIGINS=*` for cross-origin calls from another local dashboard.

For tighter production access, set `ALLOWED_ORIGINS` in `.env` to a comma-separated list, such as:

```text
ALLOWED_ORIGINS=http://localhost:3007,http://192.168.1.50:3007
```

## Food Model

Food items are stored in the `foods` table.

Required fields:

- `id`: stable string id generated by the client app.
- `name`: food, drink, restaurant item, or meal name.
- `calories`: total calories for the item.

Optional fields:

- `type`: `meal`, `restaurant`, or `drink`. Defaults to `meal`.
- `servings`: number of servings represented by the item.
- `serving`: free text description of one serving, such as `1 cup` or `half a fajita`.
- `ingredients`: free text list of ingredients.
- `source`: recipe, restaurant, brand, USDA FoodData Central, or other provenance.
- `protein`, `carbs`, `fat`: optional macro grams.

Existing foods from older schema versions are migrated to `type = 'meal'`.

## API Endpoints

Base URL examples:

- Same machine: `http://localhost:3000`
- LAN server: `http://SERVER_IP:3000`

### List Foods

```http
GET /api/foods
```

Returns all food types.

```json
{
  "configured": true,
  "foods": [
    {
      "id": "f-chicken-rice",
      "name": "Chicken breast and rice bowl",
      "type": "meal",
      "calories": 520,
      "servings": 1,
      "serving": "1 bowl",
      "ingredients": "Chicken breast, rice, salsa",
      "source": "Example"
    }
  ]
}
```

### List Meals Only

```http
GET /api/foods?type=meal
```

`MealsAndGroceryDashboard` should use this endpoint when displaying the shared meal library.

Valid filters are:

- `meal`
- `restaurant`
- `drink`

### Add Or Update A Food

```http
POST /api/foods
Content-Type: application/json
```

```json
{
  "id": "meal-taco-bowl-001",
  "name": "Taco bowl",
  "type": "meal",
  "calories": 640,
  "servings": 1,
  "serving": "1 bowl",
  "ingredients": "Rice, beef, beans, salsa, cheese",
  "source": "MealsAndGroceryDashboard"
}
```

If `type` is omitted, the API stores the item as `meal`. That means `MealsAndGroceryDashboard` can post meals without setting `type`, but setting it explicitly is clearer.

The endpoint uses upsert behavior:

- New `id`: creates the food.
- Existing `id`: updates that food.

### Remove A Food

```http
DELETE /api/foods/{id}
```

This intentionally removes the food from the shared database. Log entries that referenced the food keep their text/calorie snapshot but lose the foreign key.

## Recommended Grocery Dashboard Behavior

Use this pattern in `MealsAndGroceryDashboard`:

- Read meals with `GET /api/foods?type=meal`.
- Add meals with `POST /api/foods` and either omit `type` or set `"type": "meal"`.
- Preserve stable ids for meals created by the grocery app so edits update the existing row.
- Do not overwrite the entire `foods` table from the grocery app.
- Use `DELETE /api/foods/{id}` only when the user explicitly removes a shared meal.

## Data Safety

CaloriesDashboard no longer clears and rewrites the full food table during dashboard sync. It upserts foods it knows about, which allows another app to add meals without being wiped by a later dashboard save.

The deploy script runs `scripts/backup-db.ps1` before updating containers when a database container is already running. Backups are written under `backups/` as SQL dumps.

Migrations are additive for the shared food fields, so existing food rows are preserved and upgraded in place.
